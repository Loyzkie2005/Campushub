### 4. Functions, inputs/outputs and data flow

`CampusHubWorkerReadOnly.CurrentDirectory(pid)` reads bounded Windows x64 process parameters using QUERY_INFORMATION/VM_READ only. It first validates its own result against .NET's actual CWD; unsupported layouts or failures make verification unavailable. It reads no environment or credential fields. This is a machine-specific diagnostic, not a portable layout guarantee; see [Microsoft PEB documentation](https://learn.microsoft.com/en-us/windows/win32/api/winternl/ns-winternl-peb).

`Get-CampusHubWorkerIdentity(image, argv, cwd, backend, venv, base)` returns RuntimeKind, ResolvedManagePy and VerifiedCampusHub from explicit facts. `Get-CampusHubWorkerDescendants(snapshot, workers)` walks an existing process snapshot and returns outside descendants. `Test-CampusHubConsoleCompanion(child, parent, windowsDirectory)` returns a boolean from path/command/signature/parent/birth facts. These functions themselves do not query, stop or start a process.

`Get-CampusHubWorkerEvidence(repo)` gathers actual CIM/CWD/source facts and console signatures into Workers/OutsideChildren. `Get-CampusHubWorkerLayout(evidence)` classifies zero workers, one worker or one launcher/runtime pair; ambiguity throws. The restart saves that fresh evidence, rejects unverified descendants, then pins and stops only the approved worker handles before starting one replacement. `ConvertTo-WorkerUtc` explicitly uses DateTimeOffset UTC conversion: PowerShell's plain datetime cast can otherwise mix local and UTC clock ticks and falsely differ by eight hours.

Annotated example: child7536 with a valid System32 image/signature, exact console invocation and launcher5868 born16ms earlier is a verified companion. Change only its fixture signature to HashMismatch and it blocks mutation. The console PID is never added to the Python stop list.

`registered_fid_from_cache(rawXml, senderId)` returns the sole valid22-character registration ID from the default app's exact `|T|<sender>|*` cache entry, or None for malformed, ambiguous, legacy-token or missing data. Sender ID comes from this app's google-services.json. SDK V1 registration stores the FID in the cache's token field: see [Firebase Messaging implementation](https://github.com/firebase/firebase-android-sdk/blob/master/firebase-messaging/src/main/java/com/google/firebase/messaging/FirebaseMessaging.java) and [Store implementation](https://github.com/firebase/firebase-android-sdk/blob/master/firebase-messaging/src/main/java/com/google/firebase/messaging/Store.java). The value stays in memory and must still match the active Django device's exact account and bearer digest. No private phone value is printed or saved.

`owned_product_is_visible(nodes, productName, approvalStatus)` reads the current UI nodes passed to it and returns a boolean. It recognizes both Android text and Flutter content-desc labels, splitting merged multiline semantics. It requires the actual product name and exact current review status. The previous checker read only text, reporting false even when the screenshot showed the correct owner detail. This fixes QA evidence interpretation; no app routing logic changed. Pure tests ensure another product or wrong/missing review status cannot count as success.

### 4. Functions, inputs/outputs and data flow

`Product.approve(admin)` / `Product.reject(admin, reason)` lock the stored product, compare its previous status and persist the real review. Only a transition calls `queue_product_review(product)`. That helper takes the saved product/event timestamp and creates one existing outbox row per active, unexpired registered seller device, including `decision`. A rollback removes both status change and outbox row; the separate worker cannot read uncommitted rows.

`dispatch_delivery(delivery_id)` takes one row ID, locks delivery/device, validates current product decision/timestamp, active seller/account, recipient, session digest and expiry, then calls `send_to_installation`. The sender returns Firebase's transport ID; dispatch stores sent/failed/skipped, retries transient failures within existing limits and disables unregistered installations. No real seller is looked up by an email guess.

`presentForegroundNotification(RemoteMessage)` accepts only known review types with valid numeric routing IDs for the current account and allowed permission. It returns whether native posting succeeded. A local presentation failure does not invalidate a successfully registered Django device. There is no DND override or full-screen intent.

`_queueTap(data)` parses allowed routing IDs into `ProductNotificationTarget`; `takePendingProductNotification()` releases it only to the matching signed-in account. The app waits for existing startup/login/profile setup routing and then opens `/notifications/product`. `_load()` calls existing `SellerApplicationService.products()`, finds the exact saved ID, checks the account/token again after the asynchronous response, and passes actual data to the existing ProductDetailsScreen in owner mode. A rejected product stays outside the public catalog while its own seller can view the review reason. Expired sessions use the existing login screen, preserving the pending tap for the same owner.

Annotated example (illustrative labels only; no live record is created):

```text
Admin approves an actual saved seller product
  -> transaction commits the review + per-device outbox row
  -> existing worker verifies current seller/session and sends FCM
  -> foreground: onMessage -> Android local notification on HIGH channel
  -> background/terminated: Android displays the FCM notification payload
  -> tap: validate IDs -> existing login if needed -> owned-products GET
  -> existing Product Details shows the actual saved product/review status
```

This reuses the existing transport, authentication and details implementation instead of duplicating business logic. Inspection found Navigator/StatefulWidget navigation, not GetX, so the existing framework was retained.
