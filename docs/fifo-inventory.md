## 1. Cause / reason

CampusHub already reserves available stock when an order is placed, records completion without a second available-stock deduction, restores cancellations once, tracks exact variants and derives bundles from their components. Its former aggregate counters and movement timestamps could not prove which incoming stock was used first. FIFO adds receipt batches and allocation evidence behind those existing counters rather than replacing the Inventory workspace or order lifecycle.

The approved receiving permission is the existing `accounts.can_manage_products`, already used by stock updates. Super Admin and the built-in Marketplace Admin role have it; all SKU lookups still use existing Program/Major product scope. Inventory-only readers cannot receive stock. Movement permissions still control allocation history.

## 4. Functions / inputs / outputs / data flow

`receive(sku_id, quantity, reference, user, key)` verifies the existing permission, scoped current SKU, active approved single listing/owner, integer bounds and reference. It locks the product, updates the same available stock field/option and calls Product.save. The existing save hook records one actual stock movement and `sync_change` records the receipt batch in the same transaction. It returns `{message, batch, quantity}`. A repeated key/payload/user returns the first result; a different payload with that key fails. The UI retains the same key after timeouts/errors and across a same-tab reload until a successful response clears it.

`sync_change(sku, old, new, movement, product)` is called for every saved stock delta. It locks that SKU's batches, verifies that their remaining unallocated quantity equals the old available counter, and rejects mismatches. Receipts create receipt batches. Ordinary positive edits create **Stock adjustment** batches with unknown receiving dates, not fabricated receipts. Negative corrections allocate oldest stock with state Stock adjustment. Removed/replaced stock pools receive audited corrections; reserved variant identities cannot be retired.

Order reservation keeps the existing product/component locks and available-stock deduction. FIFO locks eligible batches ordered by opening priority, recorded time and ID, then records the exact quantities against the existing reservation movement. All batch/stock/order work is in the existing atomic order transaction. `attach(order, movement_ids)` links those allocations to the newly created actual order, including all bundle component movement IDs. The existing purchased bundle recipe remains the cancellation source.

`complete(order)` changes Reserved allocations to Consumed without decreasing available stock again. Cancellation restores only that order's Reserved allocations to their original batches, marks them Released, and retains the original priority. The existing order locks, terminal status rules and `inventory_restored` guard prevent repeat restoration. Physical On Hand remains available plus active holds.

Annotated isolated demonstration, not production data:

```text
Receipt A:20; receipt B:30; reserve order quantity25.
Allocation A:20; allocation B:5. Unallocated balances A:0 / B:25.
Before pickup: A is fully reserved, not already physically sold.
Completion: allocations become Consumed; balances stay0/25.
Cancellation instead: release to the same A/B; balances return20/30 once.
```

`order_request` supports optional `Idempotency-Key` UUID headers on the existing order endpoint. Concurrent retries with the same key/payload replay one order response; insufficient-stock/error transactions roll back. Unkeyed clients retain the existing contract: two identical requests can be two intentional orders. No Flutter update was made to start sending keys.

`reconciliation()` performs reads only and returns actual SKU balances, active-order holds, mismatch errors and a fingerprint. `initialize(expected)` locks orders/products, rechecks the fingerprint, creates opening balances and pre-FIFO held allocations, then sets the activation marker. It does not change any Product/variant quantity or invent receipt dates/movement history. Unknown references, overflow, repeated initialization or changed plans block cutover.

1. Obtain the user's explicit migration/cutover approval. Freeze all stock writers, including mobile submissions/orders and administrative edits.

Do not disable the configuration alone after cutover: that would bypass the live ledger. Schema rollback or restoring a pre-cutover backup after new transactions needs a separate reconciliation/recovery plan and explicit approval; otherwise newer transactions could be lost.

## 8. Limits / troubleshooting / learning exercise

FIFO preserves current product/variant expiry checks; batch-specific expiry and FEFO need separate business rules. Unkeyed order retries are not deduplicated by similarity. Physical-device/operating-system print-dialog testing and large-catalog performance profiling remain separate. Receiving is an authorized immediate posting, not a new multi-person approval workflow. There are no Returns or Refunds.

If FIFO shows inactive, first verify approval, applied schema, the service's actual configuration and cutover marker. Do not insert synthetic batches to hide a mismatch. If receipt retries conflict, retain/retry the original draft/key or check the recorded receipt before intentionally making a new one. A balance mismatch or missing original cancellation allocation must block the operation and be reconciled, not clamped or silently reset. Receipt dates on opening/correction rows remain unknown by design; their recording timestamps are actual cutover/correction times.

Other reporting boundaries remain: Sales Report filters creation dates while analytics uses completion/payment fallback; zero-quantity legacy eligibility differs; latest-login reporting is not a complete activity audit. Inventory report dates select product submissions, not historical stock balances. These meanings are now stated where applicable rather than changing existing date filters.
